Review a proposed small isolated Nisi U02-04 observational journal contract. You are the first Claude brainstorm/review partner. No tools or source edits. Return at most five concrete design corrections and suggested tests; no implementation. The executor will be local OpenCode; this is not product integration.

Requirements: pure ESM single source, no filesystem/clock/random; caller timestamps and ids; project/run/attempt/candidate/stage/receipt attribution. Exact id/content replay is DUPLICATE; changed content is CONFLICT. Terminal ids never new work; a retry uses new id citing terminal old id. TTL; stale heartbeat UNKNOWN never re-enqueue. Redaction declared payload field paths serialized as [REDACTED]. Revocation is a later immutable entry citing prior id, not deletion. serialize/reopen; recovered entries historical forever; no execution issuance API or authority from records. Partial serialization recovers only complete validated prefix, exact recovered ids, never claims missing tail.

Proposed simplification: immutable observation entries with states QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED, REVOKED; terminal state observations use their own immutable id. Journal is project-scoped. retryOf optional nullable requires an earlier terminal/expired/revoked observation from same run (attempt must increase). revokes optional nullable is required for REVOKED entries, refers to an earlier same-run target, and stays effective even when the revoking payload expires. Heartbeat timestamp + caller configured staleness window classified at query time, with future/invalid times refused.

Retention dilemma to resolve: hard maxEntries cap on all identities (append REFUSED CAPACITY, duplicates/conflicts still checked) is easiest but TTL only ends eligibility, and a full journal cannot append a revocation. Prefer bounded retained payloads (maxEntries newest payloads, TTL drops payload) with minimal never-deleted identity/attribution/digest tombstones; total tombstone count explicitly unbounded in this isolated contract. Original-input deterministic SHA-256 over sorted-key JSON allows exact duplicate/conflict after redaction without serializing secrets; node:crypto createHash is the only import. It is not an authentication proof.

Format idea: newline-delimited canonical JSON header + checksummed entry envelopes + footer count/chain digest. newline is commit delimiter. Missing footer/truncated final line => INCOMPLETE, malformed full line => INVALID; stop at first bad line, recover only prefix, exact ids and first bad line. A failed reopen journal is sealed against append (known prefix cannot prove absence of unseen ids). Valid complete reopen allows new ids but every recovered entry stays historical on duplicate and serialization cycles. No code/receipt revalidation, no issuance, no execution, no persistence or host ownership claims.

Trusted plain data objects only; reject unknown schema fields/statuses and malformed timestamps. Existing Nisi integrity/receipt schemas remain untouched and opaque; this new format is explicitly separate and not a replacement canonical digest profile.
