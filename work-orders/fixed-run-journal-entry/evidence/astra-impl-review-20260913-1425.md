**Journal compatibility is conditional, and the two public acceptance domains are intentionally different.**

For a completed ordinary-data `ENTRY`, I found **no intrinsic copy/entry-shape mismatch** that makes journal validation throw `ENTRY`. There is an explicit caller-dependent case: an entry with `createdAt: 100` passed to `append(entry, 99)` throws `ENTRY` at [history/run-journal-v1.mjs:83](/Users/louiscalata/nisi-next-private/history/run-journal-v1.mjs:83). Invalid/backward journal time produces `TIME`; project mismatch produces a `PROJECT` refusal; missing configured redaction paths produce `REDACTION`. In particular, `payload.adaptation.report` cannot be redacted when `adaptation` is `null`.

Conversely, the journal accepts generic representable payloads without enforcing this builder’s summary schema or key order. Reordered identity keys or unknown reason strings can therefore be journal-representable while correctly failing the builder’s summary contract. That is an intentional additional restriction, not a copy-domain discrepancy.
