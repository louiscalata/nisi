Research findings · for the brainstorm

Render Engine Reconnaissance

What current render engines, farm managers, task graphs and neural renderers already do, set against the layered, model-generated render engine we are designing — and where that design is genuinely new.

8 families surveyed · 8 vision features scored · 1 existing engine of ours as the base · 97-agent panel, 3 rounds

P0 · The vision, stated once

One model renders a frame as ten orthogonal layers — passes, not depth levels. Two other models fill the gaps: one fixes holes and seams inside a layer, the other resolves conflicts between layers. The process repeats until every cell is confident. Every (layer, tile, iteration) job is a processing node that runs in parallel on whatever hardware is free. The engine allocates that hardware and sandboxes it so nodes cannot interfere, and — the latest addition — directs the sandboxed environment like a system-on-chip for speed. Rows behave like Tetris: when a layer is full, an independent checker validates it; a cleared row is immutable and lower rows clear first.

That is eight distinct claims. The matrix below scores each one against what exists.

P1 · The field, 2026

Eight families do something adjacent to the vision. Each card names the one mechanism worth knowing about, not the product.

Offline path tracers

Blender Cycles · RenderMan XPU

Adaptive sampling estimates error by rendering twice — one accumulation with all samples, one with half — and spends further samples only where they disagree. Denoising is a separate pass (Intel Open Image Denoise, now also Unity HDRP's choice) that works better when fed auxiliary passes: albedo and normal. Path guiding learns light directions across iterations.

RenderMan 27 (Nov 2025) made XPU, the hybrid CPU+GPU renderer, final-frame capable with multi-GPU scaling — under the constraint that every GPU is identical and holds the full scene. Reported speedups: 1.8–2.3× on CPU, 5–10× on GPU, 6–15× on both.

Status: mature. Blender 5.2 LTS manual current.

Real-time engines

Unreal RDG · Unity Render Graph

A frame is a dependency graph of passes with declared resources and lifetimes. Nothing executes when recorded; once the whole frame is described, the graph is compiled, unused passes culled, transient memory aliased, and passes executed in dependency-sorted order. Unity's version is the only way to extend URP since 6.1 and "automatically optimizes the graph to minimize the number of render passes, and the memory and bandwidth" they use.

Both have offline paths: Unreal's Movie Render Pipeline / Movie Render Graph (graph-built render operations, higher quality than real time), Unity's Recorder in batch mode. Unity 6.5 (June 2026) consolidates on URP; HDRP enters maintenance, Built-In phases out.

Status: current. UE docs at 5.8; Unity 6.5.

Farm managers

OpenCue · Deadline · Flamenco

Job → Layer → Frame. In OpenCue a layer is "a frame range and a command to execute" and a frame is "an individual command". Cuebot dispatches frames to hosts whose allocation matches the layer's tag and facility; services carry minimum cores, memory and GPU requirements. Stuck frames are detected by log silence; operators retry, eat, kill, or core up.

The vocabulary coincidence matters: "layer" here is organisational, not semantic. Deadline is now also a managed cloud service (AWS Deadline Cloud, 2024). Flamenco is Blender's own.

Status: mature, ASWF-hosted (OpenCue).

Task graphs in DCCs

Houdini PDG / TOPs

A procedural dependency graph of work items. Each TOP node is a set of tasks; a downstream node instantiates its items only after upstream items complete and emit outputs, so the graph itself is generated as it cooks. Schedulers cook items in-process, out-of-process, or on a farm (HQueue, Tractor) — the graph is independent of where it runs.

This is the closest existing thing to "processing nodes generated dynamically, then distributed" — minus any notion of a generative model or convergence.

Status: mature, in every Houdini.

Neural rendering

NVIDIA DLSS 4.5 · Apple MetalFX (Metal 4)

Two fillers already ship. DLSS pairs a denoise/super-resolution model with Multi Frame Generation that produces up to five generated frames per rendered frame; 4.5 makes the multiplier dynamic, balancing frame rate, quality and latency. Apple's Metal 4 (WWDC 2025) added MetalFX Frame Interpolation and Denoising, built for unified memory, with ML inference callable inside shaders.

NVIDIA's developer page now lists a DLSS 5 with "3D-Guided Neural Rendering" — the generated pass is steered by scene geometry, i.e. by other passes.

Status: shipping; hardware-bound (Tensor cores, Apple Silicon).

Layered generative models

LayerDiffuse · LayerFusion · PSDiffusion (WACV 2026)

Models that emit layers, not one image. LayerDiffuse encodes transparency into a frozen diffusion model's latent space and trains foreground/background LoRAs; the newer work splits into two paths — generate all layers at once, or generate them sequentially — and adds harmonisation between layers (layout and appearance alignment).

This is the research literature for "a model generates ten layers", restricted to images and to a handful of layers. Harmonisation is our inter-layer reconciler, in embryo.

Status: research → early products (Runware ships LayerDiffuse).

World models

Google DeepMind Genie 3 · Project Genie

The frame is generated, not rendered. Genie 3 produces interactive worlds at 720p, 20–24 fps, holding continuity over minutes; Project Genie reached AI Ultra subscribers on 29 Jan 2026.

No passes, no farm, no verification: the opposite end of the spectrum from a durable queue. Useful as the ceiling of "a model renders" and as a reminder that convergence and correctness are our differentiators, not raw generation.

Status: limited release.

Ours, as it stands

Nisi Render Engine

A durable background render queue for Compositor and Tracker. Job-state machine, idempotent sequenced worker-event reducer, SQLite journal (jobs, attempts, frames, events, outbox), one-frame-per-slot scheduling, frame leases with expiry recovery and late-result rejection, capacity holds that keep uncertain slots, a weighted CPU admission budget with one interactive core reserved, streamed PNG verification with atomic no-overwrite promotion.

Already runs one non-render workload (forged.code-build@1). Hardware planning is CPU-slot only by its own claim string; native containment providers are defined and fail-closed.

Status: foundation, macOS-tested; Codex is write owner.

P3 · What is actually new

Three things, and only three. Everything else in the vision has a mature reference implementation somewhere in the matrix.

  • Convergent layered generation on a durable farm. Adaptive sampling (row 3) exists only inside single-process renderers; durable queues (row 7) exist only for fixed, non-iterative frames. Running "iterate until confident" as leased, recoverable farm work is unclaimed territory.
  • The line check as a commit gate. Farm managers verify that a frame exited 0; PDG verifies that expected outputs exist; this engine verifies bytes and promotes atomically. None verifies a layer as a unit with an independent reviewer and then commits rows bottom-up. That is the Tetris rule, and it has no analogue.
  • Reviewer independence as a scheduling constraint. "Author ≠ reviewer" is a property of our V5 pipeline; no render system encodes it, because no render system has models that could review. Making it a worker capability the scheduler enforces is new.

Not new, and worth saying plainly so we don't rebuild it: the dependency graph (Unreal RDG, Unity Render Graph, PDG), the two-filler split (DLSS: reconstruct within, generate between), adaptive error estimation (Cycles), leases and stuck-frame handling (OpenCue), hybrid CPU+GPU placement (XPU), and durable verified promotion (our own engine).

P6 · Unity and Unreal as the starting release point

Louis's suggestion: ship first as a render engine for Unity and Unreal. Two readings, both credible; they lead to different first releases.

Reading A — a durable queue around their renderers

The Nisi engine accepts Unreal Movie Render Pipeline / Movie Render Graph jobs and Unity Recorder batch jobs as durable background work: leases, recovery, verification, promotion, Tracker outbox — wrapped around the game engine's own renderer, which already produces frame sequences the engine knows how to verify.

For: the largest user base in real-time 3D; both engines have command-line render entry points; it exercises every existing engine component and none of the unbuilt ones. Against: headless engine installs are heavy; Unreal is Windows-first for offline quality; GPU contention with the interactive editor is exactly what the interactive reserve exists for, and it is CPU-only today.

Reading B — their render graphs as our reference architecture

Adopt RDG / Unity Render Graph as the model for the layered workload: passes with declared resources, compile-then-execute, transient aliasing, dependency sort. The layered generator becomes "a render graph whose passes are model calls".

For: it is the strongest single borrow in P4 and answers the SoC question with a proven design. Against: it is an internal architecture, not a release; on its own it ships nothing a user can point at.

Recommendation for the brainstorm: do both, in that order. Release 1 is Reading A with Unreal Movie Render Graph as the first executor kind (graph-based, CLI-submittable, offline-quality by design) and Unity Recorder second — the engine's durability and verification are the product, the game engines are the renderers. The layered generative workload lands as release 2 on the same queue, built on Reading B. Unity 6.5's consolidation on URP + Render Graph (June 2026) and Unreal's 5.8 documentation make both targets stable for the year.

P7 · The SoC question

"Direct the sandboxed environment like a SoC for faster processing" decomposes into things a scheduler can own. A system-on-chip is heterogeneous blocks, a memory hierarchy, a fabric, DMA engines, power domains and firmware that places work. The field already has the software shape of each:

  • Blocks and placement — XPU's hybrid CPU+GPU scheduling and OpenCue's allocations with per-service core/memory/GPU minimums. Ours: a block registry (P-cores, E-cores, GPU, Neural Engine via Apple Foundation Models, the PC's GPU over LAN) with capacity vectors and measured throughput, generalising the engine's CPU-slot plan.
  • Memory hierarchy and aliasing — render graphs alias transient resources and cull unused passes; Metal 4 is built around unified memory. Ours: node scratch → lane-resident cache (loaded model, prompt prefix) → immutable memory-mapped snapshot → journal.
  • Fabric and DMA — no render system models the network as a fabric, because farms assume a shared filesystem. Ours must: the PC is a chiplet behind a slow link, so placement prices the hop and stages inputs ahead of dispatch (the adaptive transport ranking already measures the links).
  • Power domains — the engine's host-power fence and capacity holds are more careful than anything in the survey; DLSS 4.5's dynamic multiplier is the model for adaptive concurrency per block.
  • The levers — macOS QoS classes and taskpolicy steer to P or E clusters (no core pinning, no GPU partitioning); Linux cgroup v2 gives full control; Windows Job Objects give CPU rate, affinity and memory limits. All of them sit inside the containment providers the engine defines and currently keeps fail-closed.

Where the speed would actually come from: locality (a lane keeps the layer context resident instead of re-sending it), overlap (staging while generating), specialisation (the Neural Engine at 0.6 s for denoise), no contention (a per-block admission budget with an interactive reserve), and cross-device parallelism. What it cannot be: a claim of SoC behaviour before a containment provider proves its controls, or a capacity figure that is configured rather than measured.

P8 · Brainstorm prompts

  1. A "layer" means three different things in the field — a Cycles pass, an OpenCue layer (frame range + command), a PDG node. Which one is ours? The manifest schema follows directly from the answer.
  2. Is the line check PDG-style ("expected outputs exist") or content verification with a reviewer model? The first is cheap and shippable in release 1; the second is the novelty in P3.
  3. DLSS makes the filler ratio dynamic. What signal drives ours — budget, latency, or the well height?
  4. Render graphs alias memory because transient resources have known lifetimes. What is the lifetime of a node's scratch, and who declares it?
  5. XPU requires every GPU to hold the full scene. Do we accept that for the PC chiplet (push the whole snapshot), or partition the snapshot per row and lose cross-row reconciliation there?
  6. OpenCue's eat skips a frame without running it. Is quarantine the same verb, and who is allowed to say it — the engine, or only a person?
  7. Release 1 as a queue around Unreal MRG: what is the one real action in the smoke test — submit a graph, watch a frame lease, see it promoted to Tracker?
  8. Genie 3 renders at 24 fps with no verification at all. Where on the line between "generated" and "verified" does each of our workload types sit, and does the manifest say so?

P10 · The panel

After P1–P9, the vision went to a design panel: five Claude lenses (working artist, studio pipeline TD, indie developer, systems architect, sceptic) across Sonnet, Opus and Haiku; then three models running on Louis's own hardware (Apple Foundation Model on-device, Bionic's qwen3.8-27b, the PC worker's Qwen3-Coder-Next 80B); then two late Claude lenses (product strategist, generative-AI-native creator). Every panelist read the others and rebutted; every candidate idea then faced three sceptical verifiers — desirability, feasibility on this design, differentiation — refuted by default when the case was generic. 97 agents, 58 ideas, 25 candidates verified.

Headline, held across all three rounds: no idea passed all three verifiers. The closest ones converge on one artefact — a sidecar written by a closed reader, with the environment (engine build, plugin version, OS + GPU + driver) inside the identity — which the verifiers call the only defensible thing on the board while insisting it is orthogonal to the queue and the tile loop.

Consensus of the local-vs-Claude paragraphs

Nobody has both halves

The locals staffed personas the first panel lacked (privacy, interop, CI) and know the machine and the wire format; the Claude lenses know the design's wounds and the business logic. None of the thirteen local ideas names a decision letter, a SPEC identity field, Lumen, temporal state or the XPU rule — they never saw the report, so the comparison is not fully fair. Six of thirteen carried a release-1 tag for work that needs lanes or closures that do not exist, because the local round had no sceptic. OpenCode's free tier hung twice and is absent.

The product lens, and what the verifiers did with it

Facts accepted: Epic's non-game per-seat fee proves a segment pays per seat; Epic maintaining MoviePipelineDeadline proves it needs a queue it does not ship; Fab and the Asset Store bill one-time, so a team tier rides on the Hub entitlement path. Conclusions refuted: "already pays Epic per seat" and "no sunk Deadline investment" pull in opposite directions; Unreal is installed on neither machine and the PC's GPU is the release-2 reconciler lane, so the engine being sold has zero dogfood evidence; a hard delivery gate at the highest-stakes step is the worst place to be a new vendor's first user. What stood: the scheduler is free everywhere (Deadline, OpenCue, Flamenco) and the money sits on the review side; and identity in source-visible software is a record, never an enforcement — the pitch may never say "prevents".

Refuted, and the refuting lens

  • One bucket-grid Watch panel — for release 1 it is Deadline Monitor in an editor window; "converging" has no meaning for a binary render (desirability, differentiation).
  • The panel as the only Accept button — the core has no user identity, and a check in Fab/UPM-distributed source is editable by the person it refuses (feasibility).
  • Local cooperative Mac + PC render of one engine frame — an engine frame cannot be split across blocks; Metal and D3D12 are not the same build (artist, architect).
  • Release-0 free checker with no daemon — reads neither engine's default output (the panel reports Recorder defaults to JPEG with Zip EXR on opt-in; MRQ's EXR defaults to PIZ); contradicts the plugin shape; no continuity into the journal (feasibility).
  • CI nightly with commit-level REPLAY — commit in the key makes REPLAY inert, file-level needs the closure that does not exist; a false REPLAY is a false green, the one thing a CI gate must never produce (feasibility).
  • Confidence-driven previz fill, generative turntables, texture patching — no image lane, no chosen validity metric; confidence collapses to cross-model disagreement alone, which decision E forbids (sceptic).
  • Open queue protocol — same-host by construction; OpenCue's protos already exist (feasibility, differentiation).
  • Show the failing check — survives only as a requirement on the manifest: {check_id, measured, threshold, scope} per attempt, which unit-02 does not record (feasibility).

Three experiments before anything is built

1 · Closure soundness, no engine — two daysExtend unit-02 with a stub executor whose inputs are a synthetic per-shot closure; drop attempt from identity; add a supersession tombstone on reopen. Pass: a vetoed attempt-0 identity never replays in a second job; an unchanged resubmit replays 100%; a package re-saved with no content change still replays.
2 · Closed reader and row gate — three days, a week if PIZ is portedStep zero: record what each engine actually writes by default and decide PIZ decoder versus UNSUPPORTED_COMPRESSION. Then 200 synthetic frames with injected NaN, missing channel and black frames, 20 legitimately dark frames and a fast cut, plus one real Recorder EXR sequence. Pass: exactly the injected cells quarantined with the right code, the assembly refused, zero false positives.
3 · Run-to-run drift, then temporal isolation — under a weekRender the same 48-frame Unity shot twice from the same commit on the same Mac, temporal off then on, and diff the sidecars: off must be bit-identical; on sets the drift floor from measurement. Then re-render frames 10–14 in isolation with GI on and measure wall time and seam difference at 9|10 and 14|15 against a threshold chosen beforehand. If either fails, "only changed frames render" leaves the release-1 pitch.
