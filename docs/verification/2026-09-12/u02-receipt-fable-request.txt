Review the following proposed Nisi v0.2 contract slice for concrete trust-boundary mistakes; return your required review schema. This is not a release or patent review.

Existing Nisi v1 engine binds adapter results to schemaVersion/runId/taskFingerprint/attempt/candidateFingerprint. The final report records stages and outcomes but trusts adapters to execute honestly. Keep these schemas and COMPLETED semantics unchanged. Its storedReportSha256 covers the PRELIMINARY report passed to a store, not the final returned report.

A private pure in-memory repository helper already captures bounded text files, rejects ambiguous ASCII/casefold paths and verifies every protected baseline digest. It overlays allowed candidate files on the baseline, preserving unchanged dependencies. A preparation binds baseline/task/candidate/materialized fingerprints. Neither preparation nor a hash is permission or evidence that a process ran.

Proposed next slice:
1. Mark preparations as factory-issued via an in-process WeakSet. createExecutionExpectation receives that preparation, runId, attempt, checkId, stage (staticChecks or tests), and an exact host-owned profile with id/version, ruleset/source/build/executable SHA256 values, argv array, environment-profile digest, fixed workspace-relative cwd and timeout. No shell strings or raw environment contents. Captured expectations have independent identities and immutable contents. Factory identity only rejects forged JS handles; it is not authentication or execution authority.
2. Closed execution receipts must match an independently supplied expectation exactly. Bind its fingerprint and its run/task/attempt/candidate/baseline/materialized/profile identities. Receipt contains process state, exit/signal, deadline/cancel/drain flags, bounded output byte counts/digests/truncation, result PASS/FAIL/NOT_RUN/ERROR/INCONCLUSIVE and bounded reason. PASS requires reported started=true, closed=true, drain=CONFIRMED, exit=0, signal=null, no interruption/error/truncation. Non-success evidence stays non-success; contradictions are refused. This only validates host statements; no actual process exists in this slice.
3. A separate closed versioned host bundle stores receipt inventory and a NEW domain-separated digest of the exact final engine report. Reader receives the expected engine-returned report and issued expectations from a trusted caller, never derives expected checks from the untrusted bundle. Each expectation corresponds to a unique report stage; run/task/attempt/candidate and adapter status must agree. Missing, extra, duplicate or cross-linked receipts are refused. FAIL/adverse bundles remain inspectable, not promoted. Output is CONSISTENT + allChecksReportedPass, authorizing=false, executionVerified=false; never certification or changed v1 status. Reader validates these links, not a complete independent re-execution of the v1 state machine or honest host.

Questions: What concrete contradictions must be rejected? What is the smallest honest relationship between native ERROR/INCONCLUSIVE and v1 UNAVAILABLE? How should a failed/unknown drain record remain readable without permitting PASS? Flag overclaims and practical missing checks only, respecting the pure-contract scope.
