Confidential bounded design review for the user's private Nisi merger. Tools and persistence must remain disabled. Review only the following contract proposal; do not claim code was executed. Return at most five concrete issues and required negative tests in the configured review schema.

Objective: implement an additive repository-snapshot contract in a Node.js library whose existing v1 workflow is unchanged. Existing v1 candidates are changed-file UTF-8 snapshots, omit unchanged files, and bind task/run/attempt/candidate IDs. The core does not read/write files or run checks. We need to bind unchanged dependencies and protected test bytes before adding a native verifier and real repository runner.

Proposed first implementation (not yet written):
1. createRepositorySnapshot({files:[{path,content}]}) captures an immutable full text snapshot, sorted by path, with per-file UTF-8 byte length/digest and a domain-separated snapshot digest. Input has exact own data fields, no accessors/symbols/custom objects/sparse arrays. Bounds: 1..1024 files, 1 MiB UTF-8 per file, 8 MiB total; well-formed Unicode content. Initial path profile is intentionally ASCII only, relative slash-separated components, no dot/dotdot/empty components, no slash escape, case collisions, trailing dots, reserved device names or file/directory-prefix collisions. It performs NO filesystem access or secret screening and grants no permission. Caller must admit file bytes separately.
2. prepareRepositoryCandidate({baseline,task,candidate,authorId}) requires a real snapshot created in this process, uses existing v1 task/candidate validators, verifies every protected baseline file exists with its declared digest, overlays permitted changed files into a new full snapshot, and refuses path/case collisions or newly exceeded bounds. It retains baseline, task, candidate and materialized snapshot digests. Baseline may include dependencies outside the writable allowlist; candidate may not edit them. Missing allowed paths may be new files; deletions/binaries/symlinks unsupported. Repeated identical content is still the workflow engine's stopping decision.
3. Returned materialization is data, not on-disk execution or a PASS receipt. No serialized object can forge snapshot factory provenance. In-process identity is not authenticated origin, permission or protection from a malicious host. Host execution receipts and run-bundle reader remain separate pending steps.

Acceptance: ordering invariance; unchanged dependency byte change alters identity; candidate overlays preserve unaffected/protected data; content mutation cannot change captured snapshot; closed schemas/invalid strings/UTF-8 budgets/case+prefix collisions; missing/mutated protected tests; out-of-scope edit; forged or serialized snapshot refused. Tests include targeted broken checks with a passing unmodified control. No package export or public v1 schema changes, no native/model execution, no publication.

Please challenge correctness, compatibility, missed identity/resource/path cases, and any acceptance claim that would exceed a pure in-memory contract. Prefer a concise useful review to a rewrite.
